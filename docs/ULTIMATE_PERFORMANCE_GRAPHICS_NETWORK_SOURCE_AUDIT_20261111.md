## B90 exact GPU source audit (2026-11-11)

- Current Ultimate has **two distinct GPU memory source representations** (real `bbport/gpu/layer/bblayer_gpu_memory.cpp/.h` and bundled emulator buffer cache). Our **layer already splits** a vertex span crossing distinct guest GPU chunks, unlike the separate bug reported in deadinside v0.7 where a grown heap crossed two pieces; copying the deadinside source patch verbatim would not be justified.
- Real B90 source defect: before arithmetic guards, guest `va+size[-1]`, physical `source.base+source.size`, mirrored `mirror.base+mirror.size` could overflow and select wrong range for invalid address requests. [B90 Draft #157](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/pull/157) rejects wrapped memory sources/mirrors/bind requests, uses safe offset subtraction and keeps guest VA split into proper spans. The active Vulkan renderer `buffer_cache_layer.cpp::LayerMirrored` bypasses the GPU resolver, so B90 also places the same guard in that original high-frequency query before its thread-local memo and address-to-block calculation. This is **defensive correctness**, not proof that normal real game geometry ever reaches invalid 64-bit addresses.
- [CI result B90](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/actions/runs/43027240917) **2/2 SUCCESS**: exact production GPU module under GCC/Clang/MSVC with opaque Vulkan handle *type stubs*, synthetic two source chunks, physical/virtual overflow, mirror residency. Test does **not** render frames or run Vulkan.
- [Official NVIDIA Reflex SDK](https://developer.nvidia.com/performance-rendering-tools/reflex) describes actual render-thread CPU/GPU queue scheduling and latency markers via Streamline or Reflex SDK+NVAPI (Windows C++). Existing Ultimate DLSS NGX bridge does not imply Reflex integration. Do not add a toggle until capability checks and real frame begin/end/present marker scheduling are implemented. NVIDIA's Frame Warp is described separately; do not falsely label ordinary Reflex low-latency mode Frame Warp.
- Further research: shadPS4 FaceGen [#1232](https://github.com/shadps4-emu/shadPS4/issues/1232), independent [deadinside v0.7 geometry and post-load FPS changes](https://github.com/deadinside28/bloodborne_pc/blob/master/docs/CHANGES_0.7.md), and [Supermedo October 2026 vertex/fp fixes](https://bbport.de/changelog/) are **candidate mechanisms**, not proof Ultimate has their original defects. GPU vendor, FaceGen/helmet, same scene and Vulkan capture required.

## B91 additional highest-page GPU-range hang prevention (2026-11-11)

[B91 Draft #158](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/pull/158) follows B90's physical and virtual memory boundary checks. In real `GpuMemory::ForEachInPlace`, an *otherwise valid* guest VA range inside the final 4-KiB virtual page previously ran `(at | 0xfff)+1` when translation failed; for that page the page-end is `UINT64_MAX`, so it wrapped the next address to 0, issued a malformed span and could loop indefinitely through unrelated low memory. This is distinct from B90's rejection of an *invalid wrapped request*. B91 selects the clipped end first, preserving forward progress without per-frame GPU synchronization or allocations. [Exact production module tests](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/actions/workflows/ultimate-batch-91-top-page-forward-progress.yml) cover last page and penultimate-to-final page, with GCC/Clang UBSan plus MSVC and execution watchdog. The test is **GPU-free** (opaque Vulkan types). There is no proven gameplay reproduction of this extreme address or user-visible FPS benefit; FaceGen, vertex cache artifacts, GPU heap-boundary stretches and low-VRAM issues must be profiled and fixed separately.

## Required test baseline and quality bars

1. **Baseline:** clean Bloodborne 1.09 with matched game region (nine CUSA variants in #84), DLC, build commit, GPU driver, machine CPU/RAM/VRAM, resolution, upscaler/FG, render patch, savedata *copy*, mods hash. Do not bundle proprietary game content with public code.
2. **Correctness gates:** 10 save-load-rejoin loops, 10 launch/exit loops; 20–60 min solo/co-op stability and longer 1–2-hour sessions. Zero memory leaks proven only from sustained stabilized working-set/VRAM slopes, not a single reading. GPU errors/driver resets, visible floor/mesh correctness and collision tracked independently.
3. **Performance:** capture GPU and CPU times separately; frametime median/p95/p99, 0.1% low and long spikes, shader build timings, PCIe readbacks/s, VRAM eviction and texture fallback, server CPU time/room, RSS and net packets/s, input-to-photon latency (Reflex markers when available). Define a threshold after real baseline; don't fabricate FPS, RTT or improvement percentages.
4. **Settings:** prefer tested, low-surprise defaults. Advanced risky optimization toggle includes availability/driver requirement, warning and rollback. One UI for launcher/client/server, with presets Smooth/Balanced/Quality/Low-VRAM/Low-Latency that map to *real* supported codepaths, not UI-only labels. Do not simultaneously force incompatible frame pacing limiters or overlays.
5. **Rollout:** all changes as Draft stacked PRs, targeted native and Windows CI, peer review, gameplay rig, profiling with reproducible machine and release-rollback manifest; no early mass rebuilds or unsafe blanket merges.
6. **Privacy & uptime:** no private Discord screenshots/game saves/credentials published; no production Fornex changes or process restarts without explicit safe deployment gate. Keep source-derived cases separate from unverified user reports and vendor marketing.
