# Ultimate B68: guest phantom-earned key items survive across sessions, without unsafe save writes

Date: 2026-11-10. Parent: [B66 Draft #132](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/pull/132). P0 [guest items missing #35](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/issues/35). Secondary [host rollback #22](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/issues/22). This is **source integration and isolated journal correctness**, not a completed gameplay fix.

## What we verified and adapted

[Upstream Yharnam Together #548](https://github.com/Amanises-Yharnam-Together/BBSC-Yharnam-Together/pull/548), MERGED: a joined guest receives badges, keys, workshop tool and similar unique goods in the game's *phantom-specific inventory list*. A guest who quits before seeing the real character's list again loses them; in the next run the boss remains dead or a chest opened and there is no way to earn the item again. The upstream author reproduced this on a rig and fixed it using a `PhantomKeyItemLedger` with file `bloodborne_party_phantom_keys_slot<N>.txt`.

Inspected upstream patches for `bloodborne_team.h/.cpp`, `bloodborne_travel.cpp`, `bloodborne_flags_store.cpp` and the GoogleTests. Its live code writes a debt file **with `std::ios::trunc`**, and it removes the file when the debt is empty, then updates `filed` whether the write succeeded. This is **dangerous** in disk-full, access-denied, AV-lock and crash scenarios: owed goods can be recorded as paid when durable storage is not. The upstream parser also **silently skips** unparseable lines, which could transform a truncated ledger into an incomplete debt and lose items. Therefore we DO NOT simply transplant its live game hook.

The user's other [ProhorovIlja/bloodborne_pc_windows_port](https://github.com/ProhorovIlja/bloodborne_pc_windows_port) and parent [visy/bloodborne_pc_windows_port](https://github.com/visy/bloodborne_pc_windows_port) supply separate save profiles and a different direct P2P protocol; their `savedata_party` approach complements but **does not replace** YT's per-character earned-goods accounting. Windows-port [Draft #89, B67](https://github.com/ProhorovIlja/bloodborne_pc_windows_port/pull/89) now preflight-recovers interrupted party copies, tests Windows/Linux. More protocol/GPU candidates remain in [intake issue #130](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/issues/130).

## Actual changes to production Ultimate C++

- `emulator/src/core/bloodborne_team.h/.cpp`: adapted upstream's **real** `OwedKeyItem`, `PhantomKeyItemsGained`, `OwedKeyItemsToGive`, `PhantomKeyItemLedger`, `EncodeOwedKeyItems` and best-effort legacy parser. Covers restart after a phantom session, consecutive phantom list identities, already-owned goods, bells excluded and idempotent return. Existing `PhantomKeyItemsToGiveBack` remains callable and game behavior unchanged until a safe transaction hook is ready.
- `ParseOwedKeyItemsStrict`: a new **fail-closed** read gate for future *persisted* debt files. Unlike upstream's legacy parser, this refuses a zero-length/truncated file, duplicated or malformed rows, CRLF canonicality errors, bells, zeros, bad counts, junk and >64KiB / >256 entries. It does not silently drop a single owed item. This is a new function not yet invoked by the game loop; all real future persistent reads MUST use it or a stricter version.
- `emulator/src/core/phantom_key_ledger_file.h`: new independent, append-only, **offline staging** utility for *future* versioned debt entries. Records are bound to an explicit save slot, **32-hex character fingerprint** and monotonically supplied sequence; filenames encode that identity. `CreateNewRevision` creates exclusive `.writer.lock` and `<revision>.pending` directories, writes a checksum and length-bound canonical goods list, reopens and verifies it byte for byte, then renames it to `.ready` without overwriting previous revisions. An empty but explicitly committed payload is a tombstone (debt discharged), **never inferred from missing/corrupt data**. `ReadReady` rejects symlink path and wrong filename/character data. A stale lock or unfinished pending revision blocks the same name and requires recovery rather than deleting last good debts.
- `emulator/tests/bloodborne/test_bloodborne_team.cpp`: adapted upstream's **5 gameplay-policy GoogleTests** (restart, second phantom, consecutive lists, same-list transitions and codec), plus a strict parser/test for no double payouts. These tests are source-integrated but must execute in actual emulator CTest before release.
- `emulator/tests/bloodborne/test_phantom_key_ledger_file.cpp`: standalone C++20 production-header test runs **GCC, Clang and MSVC** on temporary synthetic file trees: immutable revisions, unique identities, no overwriting, tombstones, stale lock, incomplete pending candidate, damaged bytes/modified identity, invalid goods, symlinks.

## Safety limitations and actual release blockers

- **Not wired to `GiveBackPhantomKeyItems` yet.** The current game loop still has the old in-process implementation. B68 therefore **does NOT claim to fix** missing items in a playable co-op game. Next step is a per-character slot identification check and fail-closed load/commit flow, with a staged debt revision written and verified **before** potentially lossy state transitions. After actual grants, wait for an authoritative *save checkpoint* before committing the owed-cleared tombstone.
- The append-only store detects accidental corruption via an FNV-1a64 checksum, **not a cryptographic MAC**. It is for local corruption checks, not adversarial tamper evidence. Even with successful file flush and rename, **OS power-loss durability cannot be promised** without platform-specific file AND directory flush. The game must not accept a pending revision as a committed record. A stale `.writer.lock` is deliberately fail-closed. New `ScanLatest(root, slot, fingerprint)` selects the highest sequence **only if every matching revision is valid**, blocks rather than falling back if any committed record is corrupt or a pending transaction exists, and ignores other character identities. This scan is still offline-only until actual game integration.
- A `character_fingerprint` in filenames has to come from the actual verified game save identity, **not** player display name or a guessed slot (new character in same slot must never inherit the prior one's goods). The new source-side `ScanLatest` implements monotonic sequence selection and conservative corrupt/pending blocking, but **actual game-level identity generation, concurrent save process guards and conflict handling must be proven separately**. Never silently fall back to an older debt if a later revision exists but is corrupt.
- Item grant/save order needs an idempotent two-phase handshake so a crash between giving an item and recording debt cleared neither deletes a due reward nor duplicates it. Upstream's `GaveBack()` immediately after `AddTradeItems` is **not** a durable save-acknowledgment.
- No Windows user saves, paid game assets, DS3 files, production Fornex, credential reads or actual game running, and no released installer. GPL-2.0-or-later for YT source adapted from same upstream; cross-port GPLv3/GPLv2-only final distribution issue remains unresolved.
- Full Windows client CMake compile, on-rig 2–5 player tests, all nine CUSA 1.09 regional game images, long multiplayer sessions and restore after process crash are still mandatory.
