# Ultimate: invasion capacity and settings ownership

Status: acceptance fixture and integration design only. No gameplay, launcher, protocol, or deployment changes in this batch.

## Invasions

- Proposed Ultimate limit: five total occupants, maximum two hostile occupants, counting held reservations as occupied on both sides. 3+2 is valid; 4+1 remains valid; 5 co-op players may still play but leave no invasion slot. An allowed maximum is not a guaranteed reservation against future co-op joins.
- Host UI: `Allow invasions` plus `Maximum invaders: 1 / 2` (default 1 when enabled; default remains off for new rooms). Two requires explicit host opt-in and compatible participants. No re-entry into a closed/private room through Quick Match. Keep current gameplay eligibility and operator kill switch; use existing cooldowns. Do not add PvP through bells to the Yharnam Together UI.
- Preserve current single-invader wire behavior for older clients. Version/capability gate the new group path; the server must own the reservation and bind the complete ordered identity set to world, connection generation and expiry. In one serialized transaction recheck current live and reserved friendly/hostile seats and assign two distinct native slots. No partial promotion: stage both joins, then admit both; revoke both on pre-commit timeout, cancellation, disconnect or invalidated target. After commit, one invader leaving should not implicitly end the other player's participation. Settings lowered below current occupancy prevent new admissions; turning invasions off uses the existing end path.
- Source constraints: `docs/INVASIONS.md` documents a solo matcher and placeholder native kind/sign values. `server/coop/invasions.h` defines a five-person ceiling, a boolean for an occupied invasion, and world and pair cooldowns. Raising only the limit does not implement identity, lifecycle or factions. Capture/verify the retail hostile slots, map transfers, hit routing and termination in 1.09 before shipping. Keep invasions relay-only initially. Never grant hostile visitors world/progress writes.
- Release checks: solo and duo in the same area, competing claims on the last seats, friendly join racing an invasion, one of a pair failing the load, stale reservation replay, room closing/host travel, boss start, host exit, different levels, and faction visibility. No release claim from this fixture alone.

## In-game settings and launcher

- Extend the existing Bloodborne System UI rather than replacing it with a separate global overlay. Existing port `Screen` options already appear in System and Insert and share `bbport.ini` keys with the launcher (see `docs/BBPORT.md`). Keep L3+R3/Insert as quick access to the same settings/actions, not another persistence system.
- System tabs in this order: Display & FPS; Graphics; Controls; Gameplay & Accessibility; Co-op & Privacy. Keep the current in-game style and gamepad navigation; use original labels and layouts where they already work. Add settings metadata with owner, scope, default, live/restart state, platform capability and fallback. Reuse current keys. Start with Screen ownership audit rather than rewriting all tabs at once.
- Player-owned: display cap and frame pacing, graphics, inputs, accessibility, local invader glow, Discord/privacy. Host-owned: enemy scaling, friendly fire, invasion permission/cap, room visibility; use existing authority and in-game team settings. The launcher may show a description but must not silently write host rules. Launcher-owned: game/install location, update channel, server selection and troubleshooting. Keep Quit to Desktop as a dedicated in-game action using the normal save/session shutdown.
- Windows/Linux first. macOS is a distinct target, not a current capability of this fork. Keep native C/C++ in engine/renderer and network critical paths; port launcher code only where profiling shows measurable benefit. Keep the current launcher UI for this iteration. Native or mod-based menu changes must check the exact game build and known original bytes; do not stack competing hooks or ship retail assets.
- Acceptance: keyboard/controller and mouse parity, focus/scroll restoration, 720p and ultrawide, no duplicate writes, save and restart behavior, unavailable controls hidden or explained, and host permission tested with a guest attempting writes. Preserve existing settings on migration and rollback. Compare against the same baseline with real game sessions before release.
