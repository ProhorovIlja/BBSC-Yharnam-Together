# BBSC: Yharnam Together — real-play acceptance matrix

Snapshot: 2026-11-22. This is a **verification plan**, not a statement that every feature is implemented or tested. It supplements [DEVELOPMENT-STATE](DEVELOPMENT-STATE.md) and [ISSUE-TRIAGE](ISSUE-TRIAGE.md); GitHub issues and exact CI runs remain the authoritative status. Focus is the *existing playable* launcher + emulated game/client + ShadNet server. The no-eboot native Windows port is paused.

## Evidence levels

- **Source-tested:** compiled production logic or unit tests against fake game state. CI success does not certify a retail game.
- **Packaged:** reproducible SHA-pinned launcher/client/server artifacts with a manifest and matching wire/protocol revision.
- **Installed:** a clean install on the target Windows machine, with independently owned legal Bloodborne 1.09 assets, exact region/CUSA and isolated disposable saves.
- **Live-verified:** actual authenticated co-op play across multiple clients/host roles, recorded output and restart/reconnect/recovery.
- **Release-ready:** all P0 acceptance gates passing, regression/rollback rehearsal and explicit owner approval for publishing/deployment. Do not promote a source-only status directly to release-ready.

No personally identifying account data, passwords, private Drive contents or decrypted/proprietary game assets belong in public CI artifacts or issue comments. Use synthetic fixtures and redacted traces. Any destructive/power-cut scenario uses **disposable test saves, a throwaway VM/disk snapshot, and a restore plan**.

## Latest source-level evidence (not a substitute for acceptance)

As of 2026-11-22, [#342](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/pull/342) passed real Qt regional-directory selection and full server Docker CI and merged, but still requires real shard affinity and direct/relay path validation. [#353](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/pull/353) rejects signed/unsigned 32-bit world-flag parser overflows; [#356](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/pull/356) checks crash-pending home archival isolation when switching character slots. Their compiled synthetic production fixture now has 31 cases, with Windows/Linux/macOS source validation. No actual Bloodborne 1.09 native save acknowledgement, disk crash-journal atomicity, or five-player GPU/network measurements were produced.

The already closed narrow #349 is a source archival-state repair; #22 remains open for cross-file crash durability and actual game saves. Keep all P0 rows UNVERIFIED until they are tested on disposable owned game files and exact pinned package SHAs.

## Run record template

For each acceptance run record: **timestamp and UTC offset; exact launcher/client/server commit SHAs, source and package SHA-256; Bloodborne version/CUSA; OS/GPU/driver; anonymized account IDs; mode; party size; host/guest/invader slots; server Hosted setting; P2P or relay path actually observed; network RTT/loss; save pre/post hashes; reproduction steps and expected/observed outcomes; relevant redacted logs and video; final PASS/FAIL/UNVERIFIED.** A failure's fix PR must be linked to both the failing run and successful rerun. Never publish raw keys or saves.

## Release and deployment gate

No production VPS, website, database or public installer changes until **all P0 rows** have actual installed/live verification and independent crash/rollback rehearsals on disposable data. P1 gaps require explicit risk tracking and user approval. A passing source CI is required but not sufficient. Keep GitHub Issues open when their specific gameplay or durability acceptance is missing; close narrow duplicates with links rather than deleting history. Protect the user's private Drive research and archives. Compare upstream GPL implementations selectively for compatible code; do not ship proprietary game files or assume cross-engine patch compatibility.
