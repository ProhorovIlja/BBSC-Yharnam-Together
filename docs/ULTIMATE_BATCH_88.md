# Ultimate B88 — fail-closed owner binding for guest pickup recovery

Date: 2026-11-11. B88 is stacked on [B87 PR #154](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/pull/154), preserving the **actual Yharnam Together** custom co-op client, transport fixes B82–B85, personal-world guard B86, and crash/rejoin pickup replay B87. Original BBSC Bell matchmaking is not used, and the separate native no-eboot PC port is not the current focus.

## Confirmed cross-process problem

B87 keys `GuestPickedFlags()` memory to `(slot, deferred_reward_character_generation)`. But the generation is initialized to 1 on every new process. A **different hunter reusing the same slot after a full restart** could therefore inherit the previous hunter's still-present `bloodborne_party_progress_slot*.txt` metadata. `ShouldReplayGuestPickupsInSession` also deliberately allows initial process bootstrap for crash/rejoin. That allows replaying the old hunter's recorded items into the new hunter, even though the in-process owner-switch tests pass. This is a **real source-level gap**; it has **not** been reproduced using a live save in this branch.

The official [Yharnam Together #566](https://github.com/Amanises-Yharnam-Together/BBSC-Yharnam-Together/pull/566) fixes guest-owned pickups on crash/rejoin *without* solving immutable save/hunter identity. Official earlier [#553](https://github.com/Amanises-Yharnam-Together/BBSC-Yharnam-Together/pull/553) isolates team-world flags from a solo guest; B86 incorporated its relevant source. Cross-source research into [Bloodborne save editor](https://github.com/Noxde/Bloodborne-save-editor) and [shadPS4 savedata issues](https://github.com/shadps4-emu/shadPS4/issues/4803) did **not** identify a validated immutable, unique in-game hunter ID usable by this code. A name is *not* that ID.

## Implemented source changes

1. `bloodborne_server_world.cpp` exposes `SettledOwnCharacterNameForPickupOwner()`: only returns the actual game's name (not the title/lobby's cached last hunter name) once the game's save-open event was observed and at least `CharacterNameSettleMs` passed. Empty/unready name is **not authorized**.
2. `bloodborne_team.cpp/.h`: pure `PickupOwnerNameMatches(recorded, active)` rejects absent, different, overlong and line-break-bearing name tokens. **Same-name hunters may still collide.** Do not use this as a unique/cryptographic ID.
3. `bloodborne_flags_store.cpp`: a new small per-save-slot `pickup_owner` metadata file binds newly recorded pickups to the observed settled in-game character name, written via the existing staged/atomic `ReplaceGuestMetadataFile`. The actual `SetGuestPickedFlags` native game-event write is prohibited unless the recorded owner matches the settled current name, regardless of whether called at map creation, at home or during a live session. The original item-list record is not rewritten to another owner's name.
4. **Legacy fail-closed migration:** a pre-B88 pickup journal with data but no `pickup_owner` binding is **retained intact but not automatically replayed or silently adopted** by a new hunter. Manual or rig-verified identity migration is required before enabling recovery of such old entries. A **new, empty journal** can be bound before saving the first pickup. An unknown name, different recorded owner, malformed old journal, missing metadata or disk write failure blocks that write/replay.
5. First pickup recorded before game name settles remains `pickup_metadata_dirty` and its atomic write is retried on subsequent `GuestProgressInterval` ticks, without losing the seen-on transition. The dirty state is dropped on a detected slot/generation change. No per-frame loops; existing 2-second observer. Under failed/unbound owner metadata, retry remains conservative, never overwriting old journal.
6. `ForgetSlotIfNewCharacter()` archives both old per-slot journal and **owner marker** before clearing them. Both marker and journal are reset, and failures are reported. No direct modification of the game's own save file.
7. Added actual emulator `GuestPickupReplay.StoredOwnerNameMustMatchActiveHunterBeforeReplay` test source; `tools/ultimate/test_batch_88_pickup_owner_bound.py` audits real native setter ordering, metadata quarantine, owner stability, retry, and the actual `tools/rig/scenarios.py` two-stage `pickup-after-guest-crash` test using the upstream verified pickup flag **52410140**. Dedicated Linux GCC/Clang and Windows MSVC smoke CI compiles/exercises the **exact production pure owner predicate**. These are *not* a substitute for the whole emulator CMake target or 2–5 live clients.

## Important remaining risks / shipping gates

- **Same-name collision is still unsafe**, and a save editor can rename an existing hunter: the game needs an immutable, verified hunter fingerprint from native save/character data. A whole-save checksum is **not** stable across autosaves; using one would block legitimate recovery. This PR cannot claim full identity isolation. Keep it Draft.
- **Existing B87 users' old metadata will not automatically restore** after B88 unless the old journal has been safely associated with the current hunter. Intentional fail-closed behavior means this is a migration compatibility concern, not a zero-impact upgrade. The journal remains on disk and is not destroyed.
- Existing [#73](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/issues/73) closed-but-empty and no-Open-prompt chests are distinct and still P0; the new rig scenario only covers the crash/rejoin pickup flag path.
- [#22](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/issues/22) host HomeWorlds migration, [#35](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/issues/35) delayed NPC/boss rewards and [#137](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/issues/137) phantom badge/tool durable save ACK all remain open. The item flag setter does **not** grant or delete native inventory.
- Check actual Windows whole-client build CI separately, then actual emulator production GoogleTests and isolated baseline-save 2/3/5-hunter crash/leave/rejoin/new hunter **same slot and same name**. Test empty owner file, malformed journal, write/rename failure, a first pickup before character name settles, and partial first-write crash. Verify no native drop duplications, progress/save integrity and no per-frame FPS regression.
- Production Fornex, live VPS/website, existing player saves, decrypted game files, installers and private screenshots remain untouched. Private handoff/history remains on **gungrain** Google Drive; do not publish private Drive file IDs or Discord screenshots in GitHub.
