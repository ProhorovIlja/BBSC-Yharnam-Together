# Ultimate B92 — GPU vertex source and VRAM mirror registry overlap isolation

Date: 2026-11-11. Stacked on [B91 Draft #158](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/pull/158), preserving the existing **Yharnam Together Ultimate playable client**, its custom co-op transport, B82–B91 fixes and separate native no-eboot port roadmap.

## Direct source bug, not a generic "vertex cache fixed" claim

`bbport/gpu/layer/bblayer_gpu_memory.h` explicitly promises that direct-memory chunks and VRAM mirrors do **not** overlap. Its production implementation `bblayer_gpu_memory.cpp`, however, allowed both:

1. `GpuMemory::AddGuestSource(physical_base, size, buffer, ...)` inserted sources into a sorted vector **without checking overlap**. `GuestSource(phys)` chooses only the source with the greatest registered base at or below `phys`. A later source beginning **inside an existing one** can therefore hide the original GPU buffer over that span and change the computed Vulkan buffer offsets. It also needlessly allocates a new `MemorySource` and a copy of the immutable vector. This violates the documented non-overlap invariant and **can** route an invalid caller's draw to the wrong buffer. It is *not* evidence that real Yharnam Together currently registers overlapping direct-memory chunks in production.
2. `GpuMemory::AddMirror(start, size, ...)` silently replaced any existing mirror with the **same start** and accepted mirrors partly overlapping an earlier or later one. `MirrorAt` / `Resolve` use sorted mirror lookup and offset subtraction to select one mirror. Overlaps can therefore hide or mis-size a live VRAM copy even if the previous GPU binding was valid. Callers in `buffer_cache_layer.cpp` already remove old mirrors before registering rebuilt/merged replacements; normal lifecycle is nonoverlapping.

Compare **actual current source**, not just names, against the independent [deadinside28/bloodborne_pc v0.7 GPU split-heap artifact note](https://github.com/deadinside28/bloodborne_pc/blob/main/docs/CHANGES_0.7.md), [shadPS4 #1232 FaceGen](https://github.com/shadps4-emu/shadPS4/issues/1232), [GPU readbacks risk #1641](https://github.com/shadps4-emu/shadPS4/issues/1641) and our [B89 external audit](ULTIMATE_PERFORMANCE_GRAPHICS_NETWORK_SOURCE_AUDIT_20261111.md). The `bbport/gpu/shim/bbport_guest_memory.cpp::RegisterChunk` caller supplies physically sorted allocation chunks to `AddGuestSource`, whereas another `BufferCache::pool_upper` path uses deliberately **overlapping** virtual windows on the same pool for Vulkan allocation offsets. These are *different* representations and **the latter is not changed by this PR**.

## B92 production patch

- Validate the two adjacent sorted physical chunks under the existing `write_mutex` using `std::ranges::lower_bound` **before** any new source vector / object allocation. Reject contained, straddling, same-start and partial overlaps without altering already registered sources. Leave physically adjacent chunks legal, including insertion at the beginning, between old chunks and at the end. Preserve existing lock-free readers of immutable source-pointer vectors and B90 arithmetic overflow checks. Normal vertex lookup and draw/dispatch path have **zero new per-draw scans**; new checks happen only when registering a chunk.
- Validate VRAM mirror `std::map` predecessor/successor under existing `mirror_mutex`, **before** `mirrors.emplace`. Reject overlap and same-start replacement rather than silently obscuring an existing mirror; permit exact adjacency (two separate Vulkan buffers). Normal read/draw path is unchanged.
- `bbport/tests/test_gpu_memory_boundaries.cpp` uses the **actual** production `GpuMemory` and existing test-only opaque Vulkan handle types: nested chunk, duplicate registration, leading overlap, insertion before/inside/after existing source ranges, overlapping and duplicate mirror, adjacent mirror, preserve old source identity/size, B90 physically split vertex spans/mirror boundaries and B91 highest-page progress.
- Dedicated `.github/workflows/ultimate-batch-92-source-overlap.yml` runs this exact production source under Linux GCC/Clang with UBSan and Windows MSVC with bounded execution. This does **not** require Vulkan, game assets or player saves, and does **not** render anything. Inherited B90/B91 CI tracks boundary and progress regression; full game-free Windows client build and real NVIDIA/AMD/Intel Vulkan game rig must still pass.

## Release / graphics and performance boundaries

These are **source-level source-registration invariant** improvements, not measured vertex-explosion cures, VRAM drops, FPS gains, shader fixes, GPU readbacks fixes, FaceGen fixes or longer-session crash fixes. Existing core module already splits a valid guest VA across two distinct physical GPU buffers; that is different from deadinside's expanded-heap issue. Enabling strict readbacks everywhere can hurt performance and stability; current Ultimate's `BB_READBACKS` is already `Relaxed` by default, so merely setting that value again is not a feature. NVIDIA Reflex needs a genuine SDK/Streamline/NVAPI backend and latency measurement, not a fake UI toggle. No live performance claims or unreal "zero bugs" status.
