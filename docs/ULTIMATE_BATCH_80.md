# Ultimate B80: preserve pre-grant earned goods across rapid rejoin; gate own key-item top-ups

Date: 2026-11-11. Stacked on [B79 Draft PR #145](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/pull/145) in the playable Ultimate track. Key-item issue [#137](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/issues/137) remains P0; unrelated native deferred item-lots [#35](https://github.com/ProhorovIlja/BBSC-Yharnam-Together/issues/35) remain open.

## Two source-verified active gameplay failure windows

1. B76/B77 only preserved the original first/last phantom snapshot when `return_attempt.Requested()` became true (or when the secondary ledger was already active). A player could earn a badge in guest world A and immediately connect to guest world B **without returning home and without any native grant attempt**. The real `GiveBackPhantomKeyItems` branch then observed a different `KeyItemList` pointer, unconditionally reassigned `phantom_list`, `first_look`, `last_look` and lost the only observations of A's earned item. B80 routes the second list to B77's genuine secondary `PhantomKeyItemLedger` whenever the original phantom has pending gains, regardless of whether `GiveItems` has been called.
2. When a player joined their *first* phantom inventory, the real code called `OwnKeyItemsForPhantom` and `AddTradeItems` to put their preexisting badges/tools into the phantom's list, but committed the phantom list pointer and snapshots **before** checking whether the native item-giving hooks and `MapItemMan` were ready. B74 only protected grants on return to home, not this guest top-up. Native `AddTradeItems` can silently drop a grant if the manager is unavailable during a scene load; the list would then be treated as processed without retry.

## Actual production changes

- `emulator/src/core/phantom_inventory_scope.h`: portable pure `PreserveFirstPhantomOnRejoin(second_lane_active, native_grant_attempted, first_list_seen, next_list_differs, first_has_gains)` returns true on an already active second lane, an in-flight/ambiguous native request, **or a different new phantom list when the first has earned goods even before a native request**. This is an in-process state policy, not durable storage or server authority.
- `emulator/src/core/bloodborne_travel.cpp::GiveBackPhantomKeyItems`: evaluate `PhantomKeyItemsGained(first_look,last_look)` before any new original-list mutation on rapid rejoin. When gains exist, keep the original first snapshot and pass new observations to the second production ledger, which tracks subsequent phantom lists separately without native grants while the first remains unresolved.
- On normal first-phantom entry, read a bounded key list once (`<=256` entries). Compute own top-ups. **If they are nonempty and `TradeItemsReadyToGive()` is false, return before updating `phantom_list`, `first_look` or `last_look`**. On later game-thread ticks the new list is retried. If no top-ups are needed, do not require the manager or stall entry. If ready, call the existing void-return native grant and log it as *requested*, not confirmed.
- Extend native `test_phantom_inventory_scope.cpp` for policy permutations including the pre-grant/non-empty/changed-list case and owner validity. Real `test_bloodborne_team.cpp` GTest exercises first unpaid phantom badge, second/third rejoin, and **same-item deduplication**: after observing the first 4114 badge in the hunter's own list, the second ledger does not request it again, only other missing goods.
- Source-extracted production `PhantomKeyItemLedger` C++20 GCC and Clang executable regression includes the duplicate case. Dedicated B80 GitHub CI also executes actual Windows MSVC C++20 policy tests and syntax-compiles real `bloodborne_trade.cpp`, `bloodborne_travel.cpp`, `bloodborne_team.cpp` and `test_bloodborne_team.cpp` C++23 translation units against pinned `fmt/spdlog` and generated real protobuf. B76/B77 inherited contracts updated for the new branch ordering.

## Precise safety boundaries

The initial own-key top-up is still a native **void-return**, not an acknowledged, idempotent transaction: even after `TradeItemsReadyToGive()` returns true, the game can reject a grant later. B80 does not automatically replay ambiguous top-ups; it only prevents the proven immediate failure while game hooks are unavailable. Game-frame snapshots, receipt of home items and the B68–B79 offline immutable journal are **not a disk-save acknowledgement**. No stable per-hunter identity across process restarts, authenticated save ACK, journal write-before-native-give, fsync/power-loss ordering, 2–5 live hunter rig or definitive duplicate/loss recovery. Never claim P0 #137 fixed or distribute a stable binary. No savedata/Forneх production/game asset mutation.
